# 架构偏离分析

**参考文档**: `README.md`（架构设计说明）  
**分析日期**: 2026-04-16  
**说明**: 本文档仅记录偏离情况，暂不修改代码。

---

## 1. 新增了 README 未定义的项目层

### 1.1 `Foundation.Building` — 未在架构中定义

**架构规定**: `Shared` 层只有 `Foundation.Core`（纯算法/几何）和 `Foundation.Cad`（CAD API 封装）。

**实际情况**: 新增了 `MetroToolKits.Foundation.Building`，包含 `BuildingElement`、`Wall`、`Slab`、`Column`、`ElementTypeDefinition` 等建筑构件类。

**偏离原因**: 这些类被 Core 层和 Infrastructure 层同时使用，放在 Shared 层是合理的扩展，但 README 的架构图和依赖关系图中没有体现。

---

### 1.2 `CadAdapter` — 未在架构中定义

**架构规定**: SectionGenerator 的分层为 Core / App / Infrastructure / Plugin，没有 CadAdapter 层。

**实际情况**: 新增了 `MetroToolKits.SectionGenerator.CadAdapter` 项目，包含 `CadDrawingService`（绘制块）等 CAD 适配实现。

**偏离原因**: 开发时将"绘图服务"从 Infrastructure 中独立出来，形成了一个额外的适配层。按架构规定，这部分内容应归属于 Infrastructure 层（实现 App 层定义的接口）。

---

## 2. 依赖关系偏离

### 2.1 App 层直接依赖 Bootstrap.Logging

**架构规定**: App 层依赖领域层和基础设施层接口，不应依赖 Bootstrap 层。

**实际情况**: `GenerateSectionUseCase.cs` 和 `UpdateSectionUseCase.cs` 直接 `using MetroToolKits.Bootstrap.Logging`，注入了 `UserLogger`（Bootstrap 层的具体类）。

```csharp
// GenerateSectionUseCase.cs
using MetroToolKits.Bootstrap.Logging;  // ← 跨层依赖
...
private readonly UserLogger _userLogger;
```

**偏离影响**: 违反了"依赖倒置"原则。App 层应依赖接口（如 `IUserLogger`），由 Bootstrap 层注入具体实现。目前 App 层与 Bootstrap 层产生了循环依赖风险。

---

### 2.2 Core 层依赖 Foundation.Building（可接受但需说明）

**架构规定**: Core 层"仅依赖 `Foundation.Core`"。

**实际情况**: `SectionComposer`、`MultiFloorSectionComposer`、`FloorGeometryHasher` 均依赖 `Foundation.Building`（`BuildingElement`、`Wall` 等）。

```xml
<!-- MetroToolKits.SectionGenerator.Core.csproj -->
<ProjectReference Include="..\..\..\Shared\MetroToolKits.Foundation.Building\..." />
```

**偏离说明**: 由于 `Foundation.Building` 本身是 Shared 层（无 AutoCAD 依赖），这个依赖在技术上不违反"领域纯净"原则，但与 README 中"Core 层仅依赖 Foundation.Core"的表述不符。

---

### 2.3 Infrastructure 层直接依赖 Core 层具体类

**架构规定**: Infrastructure 层"依赖应用层接口、Foundation.Core"，不应直接依赖 Core 层具体实现。

**实际情况**: `XDataSnapshotRepository` 直接使用 `SectionSnapshot`（Core 层数据模型），`LayerBasedElementRecognizer` 直接使用 `BuildingElement` 子类（`Wall`、`Slab`、`Column`）。

**偏离说明**: 数据模型类（`SectionSnapshot`、`FloorSnapshot`）放在 Core 层是合理的，但按严格分层，这些 DTO 应放在 App 层的 Abstractions 中，或单独的共享模型层。

---

## 3. 测试项目命名偏离

**架构规定**: 测试项目命名为 `MetroToolKits.Foundation.Core.Tests`、`MetroToolKits.SectionGenerator.Core.Tests`、`MetroToolKits.Integration.Tests`。

**实际情况**:
- `MetroToolKits.Tests.Foundation`（命名顺序不同）
- `MetroToolKits.Tests.SectionGenerator.Core`（命名顺序不同）
- 缺少 `MetroToolKits.Integration.Tests`

**偏离影响**: 仅命名风格问题，不影响功能。

---

## 4. 目录结构偏离

### 4.1 缺少 `Extras` 目录

**架构规定**: `src/Plugins/Extras/MetroToolKits.Extras.Commands/` 用于收容小脚本。

**实际情况**: 该目录不存在，所有命令都在 SectionGenerator.Plugin 中。

---

### 4.2 Foundation.Core 缺少 `Mathematics` 子目录

**架构规定**: `Foundation.Core` 应有 `Geometry/` 和 `Mathematics/` 两个子目录。

**实际情况**: 只有 `Geometry/`，没有 `Mathematics/`（插值、变换、单位转换等）。

---

### 4.3 Foundation.Cad 缺少 `Abstractions/` 和 `Extensions/` 子目录

**架构规定**: `Foundation.Cad` 应有 `Abstractions/`（接口定义）、`Services/`（实现）、`Extensions/`（扩展方法）三个子目录。

**实际情况**: 只有 `Services/`，接口和实现混放在同一目录，没有 `Extensions/`。

---

### 4.4 Infrastructure 目录结构与架构不符

**架构规定**: Infrastructure 只有 `Config/` 子目录。

**实际情况**: 实际有 `Config/`、`Recognition/`、`Repositories/`、`Services/` 四个子目录，内容远超架构预期（这是功能扩展的自然结果，属于合理偏离）。

---

## 5. Bootstrap 层职责扩展

**架构规定**: Bootstrap 层负责"统一插件入口、DI 容器初始化、命令动态注册"。

**实际情况**: Bootstrap 层额外承担了：
- 日志系统初始化（`AcadEditorLogger`、`FileLogger`、`UserLogger`）
- 配置文件加载（`appsettings.json`）
- `UserLogger` 具体类定义（被 App 层直接依赖，见偏离 2.1）

**偏离说明**: 日志和配置放在 Bootstrap 层是合理的，但 `UserLogger` 作为具体类被 App 层直接引用，打破了层间隔离。

---

## 6. `CommandRegistry` 实现与架构描述不符

**架构规定**: 命令通过 `RegisterCommand<T>(string commandName)` 动态注册，AutoCAD 命令方法应通过 `[CommandMethod]` 特性标记。

**实际情况**: `CommandRegistry.RegisterCommand<T>` 只是将类型存入字典，并没有实际向 AutoCAD 注册命令。真正的命令注册依赖各命令类上的 `[Autodesk.AutoCAD.Runtime.CommandMethod]` 特性，这是 AutoCAD .NET API 的标准机制，在程序集加载时自动生效。

**偏离说明**: `CommandRegistry` 目前是一个空壳，实际命令注册由 AutoCAD 运行时通过反射完成，与架构描述的"动态注册"机制不完全一致。

---
